# Technical Specification & Implementation Guide: Real-Time Doubt-Solving Platform

This document serves as the master engineering specification for developing the real-time doubt-solving web application.

---

## 1. System Overview & Architecture

### 1.1 Core Value Proposition

A low-latency marketplace/platform connecting students posting academic doubts with qualified solvers competing to claim and answer them.

### 1.2 Key System Requirements

1. **High-Concurrency Atomic Locking:** Multiple solvers clicking "Claim/Lock" simultaneously on the same doubt must resolve deterministically at the database level with zero race conditions.
2. **Instant Feed Invalidation:** Real-time updates push lock states to all active solvers using WebSockets, preventing stale clicks.
3. **Strict Security Perimeter:** App-Check style device/client attestation prevents bot abuse without degrading latency on high-frequency solver endpoints.
4. **End-to-End Type Safety:** Zero manual API glue code; Hono RPC (`hc<AppType>`) ensures changes on backend router parameters immediately trigger compile-time type errors on the frontend.
5. **Static Frontend Footprint:** Zero SSR in production; the client compiles to static assets hosted on edge CDNs (e.g., Cloudflare Pages) with build-time prerendering for public routes.
6. **Strict Code Quality & File Size Rule:** Every component and module file MUST be **< 150 lines**. Break complex features into small, concise, single-responsibility components and composable hooks.

### 1.3 Tech Stack Selection

- **Monorepo Manager & Runtime:** [Bun](https://bun.sh) (`bun workspaces`: `frontend`, `backend`)
- **Linter & Formatter:** [Biome](https://biomejs.dev) (configured via root `biome.json` and `.zed/settings.json`)
- **Backend API Framework:** [Hono](https://hono.dev) with Hono RPC (`hc`)
- **Database Engine:** PostgreSQL 16+ (running on VPS or managed DB)
- **Database Driver & ORM:** `postgres.js` + [Drizzle ORM](https://orm.drizzle.team)
- **Real-time State / PubSub:** Redis (Dragonfly or Redis 7+) + Native Bun WebSockets
- **Object Storage:** Cloudflare R2 (S3-compatible, presigned upload URLs)
- **Authentication:** [Better-Auth](https://better-auth.com) with Drizzle adapter + RBAC plugin (auth schema generated via `@better-auth/cli`)
- **Frontend Framework:** React 19 + [React Router v7](https://reactrouter.com) (Framework Mode, `ssr: false` SPA with selective prerendering)
- **Frontend State Management:** [TanStack Query v5](https://tanstack.com/query) (global query cache, `useSuspenseQuery` for fetching, `useMutation` for mutations, WebSocket sync)
- **Form & Validation Layer:** [Conform](https://conform.guide) + [Zod](https://zod.dev)

## 3. Database Schema Design (Drizzle ORM)

### 3.1 Better-Auth Schema Generation

Better-Auth tables (`user`, `session`, `account`, `verification`) are **generated automatically using the Better-Auth CLI**, not written manually:

```bash
bunx @better-auth/cli generate --config ./src/lib/auth.ts --output ./src/db/auth-schema.ts
```

### 3.2 Domain Schema Definition (`backend/src/db/schema.ts`)

Application domain tables import and reference the generated `user` table:

```typescript
import {
  pgTable,
  serial,
  text,
  varchar,
  timestamp,
  integer,
  pgEnum,
  index,
} from "drizzle-orm/pg-core";
import { relations } from "drizzle-orm";
import { user } from "./auth-schema"; // Generated by Better-Auth CLI

export const doubtStatusEnum = pgEnum("doubt_status", [
  "UNLOCKED",
  "LOCKED",
  "RESOLVED",
  "EXPIRED",
]);

// Doubts Table
export const doubts = pgTable(
  "doubts",
  {
    id: serial("id").primaryKey(),
    title: varchar("title", { length: 255 }).notNull(),
    description: text("description").notNull(),
    subject: varchar("subject", { length: 64 }).notNull(),
    imageUrl: text("image_url"),
    status: doubtStatusEnum("status").default("UNLOCKED").notNull(),
    studentId: text("student_id")
      .references(() => user.id)
      .notNull(),
    solverId: text("solver_id").references(() => user.id),
    lockedAt: timestamp("locked_at"),
    resolvedAt: timestamp("resolved_at"),
    createdAt: timestamp("created_at").defaultNow().notNull(),
    updatedAt: timestamp("updated_at").defaultNow().notNull(),
  },
  (table) => [
    index("idx_doubts_status_created").on(table.status, table.createdAt),
    index("idx_doubts_subject").on(table.subject),
  ],
);

// Solutions / Answers Table
export const solutions = pgTable("solutions", {
  id: serial("id").primaryKey(),
  doubtId: integer("doubt_id")
    .references(() => doubts.id)
    .notNull(),
  solverId: text("solver_id")
    .references(() => user.id)
    .notNull(),
  content: text("content").notNull(),
  attachmentUrl: text("attachment_url"),
  createdAt: timestamp("created_at").defaultNow().notNull(),
});

// Relations
export const doubtsRelations = relations(doubts, ({ one, many }) => ({
  student: one(user, { fields: [doubts.studentId], references: [user.id] }),
  solver: one(user, { fields: [doubts.solverId], references: [user.id] }),
  solutions: many(solutions),
}));
```

## 4. Backend Implementation (Bun + Hono)

### 4.1 Atomic Concurrency: Locking Algorithm

Never use `SELECT FOR UPDATE` followed by `UPDATE` in separate queries. Execute atomic conditional row updates directly using PostgreSQL's row-level locking.

```typescript
// backend/src/modules/doubts/doubts.service.ts
import { db } from "../../db";
import { doubts } from "../../db/schema";
import { eq, and, or, lt, sql } from "drizzle-orm";

const LOCK_TIMEOUT_MINUTES = 15;

export async function claimDoubtAtomic(doubtId: number, solverId: string) {
  const expirationThreshold = new Date(
    Date.now() - LOCK_TIMEOUT_MINUTES * 60 * 1000,
  );

  const [claimed] = await db
    .update(doubts)
    .set({
      status: "LOCKED",
      solverId: solverId,
      lockedAt: sql`NOW()`,
      updatedAt: sql`NOW()`,
    })
    .where(
      and(
        eq(doubts.id, doubtId),
        or(
          eq(doubts.status, "UNLOCKED"),
          // Re-claimable if locked solver timed out
          and(
            eq(doubts.status, "LOCKED"),
            lt(doubts.lockedAt, expirationThreshold),
          ),
        ),
      ),
    )
    .returning();

  return claimed || null;
}
```

### 4.2 Bot Defense: App-Check Token Exchange

Verify Turnstile once on auth/session creation and issue a signed, short-lived Attestation Token.

```typescript
// backend/src/middleware/app-check.ts
import { createMiddleware } from "hono/factory";
import { verify } from "hono/jwt";

const ATTESTATION_SECRET = process.env.ATTESTATION_SECRET!;

export const appCheckMiddleware = createMiddleware(async (c, next) => {
  const token = c.req.header("X-App-Check-Token");
  if (!token) {
    return c.json({ error: "Missing App-Check attestation" }, 403);
  }

  try {
    const payload = await verify(token, ATTESTATION_SECRET);
    if (!payload || payload.iss !== "doubt-app-attestation") {
      return c.json({ error: "Invalid attestation source" }, 403);
    }
  } catch {
    return c.json({ error: "Attestation expired or corrupt" }, 403);
  }

  await next();
});
```

### 4.3 WebSocket Engine: Broadcast Lock Changes

```typescript
// backend/src/ws/hub.ts
import type { ServerWebSocket } from "bun";

export type WSData = { userId: string; role: string };

class FeedHub {
  private sockets = new Set<ServerWebSocket<WSData>>();

  add(ws: ServerWebSocket<WSData>) {
    this.sockets.add(ws);
  }

  remove(ws: ServerWebSocket<WSData>) {
    this.sockets.delete(ws);
  }

  broadcast(event: string, data: Record<string, unknown>) {
    const message = JSON.stringify({ event, data, ts: Date.now() });
    for (const ws of this.sockets) {
      ws.send(message);
    }
  }
}

export const feedHub = new FeedHub();
```

### 5.2 Singleton QueryClient & Router Context (`frontend/app/lib/tanstack-query.ts`)

To avoid recreating the cache across client-side navigations and ensure route loaders share the same instance:

```typescript
import { QueryClient } from "@tanstack/react-query";
import { createContext } from "react-router";

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 1000 * 60 * 2, // 2 minutes
      refetchOnWindowFocus: false,
    },
  },
});

export const queryContext = createContext<QueryClient>();

export function getContext() {
  return new Map([[queryContext, queryClient]]);
}

export function getQueryClient(context: Readonly<Map<unknown, unknown>>) {
  const client = context.get(queryContext);
  if (!client) {
    throw new Error("QueryClient not found in Router context");
  }
  return client as QueryClient;
}
```

### 5.3 Client Entry Point (`frontend/app/entry.client.tsx`)

```tsx

import { startTransition, StrictMode } from "react";
```

### 5.4 Data Fetching Convention (Suspense + `clientLoader`)

Data fetching follows the canonical pattern established in [`frontend/app/routes/_index.tsx`](file:///E:/Programming/term-break-projects/achieve-doubts/frontend/app/routes/_index.tsx):

1. **Query Options:** Define standard TanStack `queryOptions`.
2. **Preload in `clientLoader`:** Retrieve `queryClient` from `context` and trigger fetching before transition completes.
3. **Render with Suspense:** Components consume data using `useSuspenseQuery(...)` inside `<Suspense fallback={...}>`.

```tsx
// Example: frontend/app/routes/_index.tsx
import { queryOptions, useSuspenseQuery } from "@tanstack/react-query";
import { Suspense } from "react";
import { getQueryClient } from "~/lib/tanstack-query";
import type { Route } from "./+types/_index";

export const getList = queryOptions({
  queryKey: ["list"],
  queryFn: async () => {
    return ["item1", "item2", "item3"];
  },
});

export function clientLoader({ context }: Route.ClientLoaderArgs) {
  const queryClient = getQueryClient(context);
  queryClient.query(getList);
  return null;
}

function List() {
  const { data } = useSuspenseQuery(getList);
  return (
    <ul>
      {data.map((item) => (
        <li key={item}>{item}</li>
      ))}
    </ul>
  );
}

export default function Home() {
  return (
    <div>
      <Suspense fallback={<div>Loading...</div>}>
        <List />
      </Suspense>
    </div>
  );
}
```

### 5.5 Mutations with `useMutation`

All write operations (creating doubts, claiming doubts, submitting solutions) are handled directly via TanStack Query's `useMutation` hook rather than React Router action forms, preserving tight client-side RPC type safety and optimistic UI invalidation:

```tsx
// frontend/app/features/doubts/use-claim-doubt.ts (< 150 lines)
import { useMutation, useQueryClient } from "@tanstack/react-query";
import { api } from "~/lib/api";

export function useClaimDoubt(doubtId: number) {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async () => {
      const res = await api.api.doubts[":id"].claim.$post({
        param: { id: String(doubtId) },
      });
      if (!res.ok) {
        const err = await res.json();
        throw new Error(err.error || "Failed to claim doubt");
      }
      return res.json();
    },
    onSuccess: () => {
      // Invalidate both the specific doubt and solver feed cache
      queryClient.invalidateQueries({ queryKey: ["doubts", doubtId] });
      queryClient.invalidateQueries({ queryKey: ["doubts", "feed"] });
    },
  });
}
```

## 7. Component Structure & Quality Standards

- **Maximum 150 Lines per File:** Any component or helper exceeding 150 lines must be refactored into sub-components, dedicated hooks (`features/<feature>/use-*.ts`), or pure utility modules.
- **Feature Co-Location:** Place domain-specific UI, hooks, and queries together under `frontend/app/features/<feature-name>/`.

## 8. Development & Deployment Roadmap

### Phase 1: Local Development Setup

1. **Monorepo Setup:** Run `bun install` across workspace packages (`frontend`, `backend`).
2. **Database & Cache:** Run PostgreSQL and Redis via Docker Compose.
3. **Better-Auth Generation:** Run `bunx @better-auth/cli generate` in `backend` to scaffold authentication tables.
4. **Run Migrations:** Initialize Drizzle schema with `bun run --cwd backend drizzle-kit push`.

### Phase 2: Core Feature Implementation

1. **Doubt Ingestion:** Student uploads image to Cloudflare R2 presigned URL and posts record with App-Check token.
2. **Solver Feed:** Implement the real-time unlocked doubts view with WebSocket subscription.
3. **Atomic Claiming:** Implement `claimDoubtAtomic` in backend and trigger immediate Redis pub/sub broadcast.
4. **Answer Submission:** Solver submits answer via `useMutation`, updating status to `RESOLVED`.

### Phase 3: Build & Production Deployment

1. **Client Build:** Execute `bun run build` inside `frontend`. Verify that build output contains prerendered HTML files for marketing pages and an `index.html` fallback for SPA routes.
2. **Static Edge Deploy:** Deploy `frontend/build/client` to Cloudflare Pages (configure rewrite fallback `/*` to `/index.html`).
3. **Server Containerization:** Package Bun backend with a multi-stage Dockerfile and deploy to VPS behind a reverse proxy (e.g., Traefik/Caddy).
